# Явная проверка владения состоянием компонента — #16

## Цель и выбранное подключение

В выбранных потребителем бизнес-компонентах диагностировать прямое создание
локального логического состояния. UI-Kit может владеть локальным состоянием,
не используя глобальный бизнес-state. Решение для его тестируемой организации
вынесено в [#27](https://github.com/antonsmolko/gost-kit/issues/27).

Владелец выбрал обычные ESLint overrides:

```ts
export default [
  ...(await createSvelteConfig({ tsconfigRootDir })),
  {
    files: ['src/**/*.svelte'],
    rules: { 'gost/no-component-state': 'error' },
  },
  {
    files: ['src/ui-kit/**/*.svelte'],
    rules: { 'gost/no-component-state': 'off' },
  },
];
```

`src/ui-kit` — пример пути, не обязательная структура. Вместо исключения можно
сразу включить правило только на нужных бизнес-каталогах. Оно не угадывает роль
компонента по имени файла или FSD. Остальные lint-проверки в UI-Kit сохраняются.

Автоматическое включение запрета для всех Svelte-потребителей не выбрано.
Дополнительного параметра `architecture` или режима `fc-presenter` не будет.
Functional core и presenter — отдельные ответственности. Настройка базового
`createSvelteConfig` и существующее правило #6 сохраняют свои текущие границы.

## Минимальная первая версия

Новое правило `gost/no-component-state` экспортируется существующим plugin.
В factory оно доступно через уже зарегистрированный `gost`, но автоматически
не включается. В авторском примере подключаем его явно к `.svelte` компонентам.
Дополнительная область rune-модулей может задаваться потребителем явно;
на все `.svelte.ts` запрет по умолчанию не распространяется. Imperative shell
с существующим `$state.raw` остаётся за пределами такого component override.

Диагностируем прямые настоящие rune-вызовы `$state(...)`, `$state.raw(...)`
и `$bindable(...)` в выбранном файле. `$bindable` объявляет writable prop,
который не соответствует выбранной для этих компонентов границе ready props
и intent callbacks. Проверяем instance/module scripts и создание состояния
во вложенных функциях/классах файла; перенос в локальный helper не является
исправлением владения состоянием. Локальные функции с совпадающим именем
отличаем через lexical bindings.

`$props`, `$derived`/`$derived.by`, готовые props, константы и импорты чистых
presenters остаются разрешёнными. Не запрещаем обычный `let` и не считаем
`$derived` созданием второго mutable store. Вычисления внутри derived — #19,
бизнес-ветвления/dispatch — #17, условия шаблона — #18.

## Browser refs

Разрешаем простой instance-local DOM/component ref, непосредственно связанный
с `bind:this` того же компонента:

```svelte
<script lang="ts">
  let input: HTMLInputElement | undefined = $state();
</script>

<input bind:this={input} />
```

Для исключения нужен прямой identifier declarator, пустое/undefined/null
начальное значение и прямая привязка `bind:this` к тому же binding.
Совпадение имён разных переменных недостаточно. Module-script refs, объекты
логического состояния с ненулевым initializer и произвольное объявление
`$state()` без соответствующего `bind:this` не получают это исключение.
Более сложный browser adapter можно вынести в отдельно выбранную область
без правила или обосновать узким ESLint disable; семантика adapter не угадывается.

## Контракт и пределы диагностики

Для выбранных бизнес-компонентов logical feature/UI state меняется через
согласованный root/feature state и intent actions. Прямые записи в этот state,
изменение incoming props и writable derived overrides не соответствуют контракту.
Но первая версия этого правила проверяет создание через перечисленные runes,
а не доказывает отсутствие всех мутаций, aliases или второго mutable владельца.

Обычные let-переменные могут быть временными значениями/browser handles.
Их нельзя запретить одним синтаксическим гейтом. Анализ записей через props,
двусторонние `bind:value`/`bind:checked`, внешние factories и скрытые helpers
не включается в обещания первой версии. Эти конструкции требуют отдельной
проверки владения; успешный lint не объявляется доказательством всей архитектуры.

Автофикса и автоматического переноса состояния нет: для такого переноса нужно
выбрать действия, state/reducer contract и lifecycle. Сообщение указывает rune
и предлагает перенести логическое состояние к принятому владельцу либо
явно исключить самостоятельный UI-компонент из этой области проверки.

## Сценарии проверки

| Сценарий                                                    | Ожидаемое поведение                                    |
| ----------------------------------------------------------- | ------------------------------------------------------ |
| `let isOpen = $state(false)` в выбранном компоненте         | Ошибка без fix                                         |
| `$state.raw({ draft: '' })`                                 | Ошибка без fix                                         |
| `$bindable()` в default props                               | Ошибка без fix                                         |
| Rune в module script/helper/class выбранного файла          | Ошибка без fix                                         |
| `$props`, отдельный feature selector и вызов presenter      | Без ошибки этого правила                               |
| Stateless/shared компонент с готовыми props/callback        | Без ошибки                                             |
| Прямой instance ref с пустым initializer и `bind:this`      | Без ошибки                                             |
| Одинаковые имена разных bindings, отсутствующий `bind:this` | Не дают ref-исключение                                 |
| Логическое значение с initializer и `bind:this`             | Не даёт ref-исключение                                 |
| Обычный `let`, временный browser handle                     | Не запрещается сам по себе                             |
| UI-Kit path с поздним override `off`                        | Локальное состояние разрешено, другие checks действуют |
| Только базовый `createSvelteConfig`                         | Новое правило выключено                                |
| Существующий shell module вне component override            | Поведение сохраняется                                  |

RuleTester проверяет rule ID, сообщения и отсутствие fix. Настоящий ESLint с
Svelte parser проверяет component scripts, ref-binding и включение/исключение
по glob. Синтаксически допустимые policy-negative случаи не подменяются parser
errors. Собранные plugin/config tarballs проверяются во внешнем consumer.
Полный check и существующие browser tests защищают интеграцию примера.

## Основания и статус

Источник требований — [#16](https://github.com/antonsmolko/gost-kit/issues/16)
и уточнения владельца о независимом UI-Kit и явном подключении правила.
Точные browser/ready-props границы сверены с предложением FRONTEND-ARCH-001/002
в gost-spec PR #81, revision `3edc7eb79115fa3f4f8a0c78d3e9f6d6813edd1c`.
Тот PR пока открыт, документы proposed: этот дизайн не объявляет их принятыми
или обязательными для всех проектов. #27 остаётся отдельной будущей работой.

После слияния PR #28 владелец поручил брать следующую задачу. Реализация #16
продолжается по этому дизайну, выбранным overrides и исключениям UI-Kit.

  explicit on без fix, UI-Kit off с сохранением button rule, DOM ref и shell
  проверены. Публичные TypeScript-декларации проходят typecheck; artifacts не
  содержат исходники/тесты и не устанавливают `@gost-kit/common`/`@gost-kit/svelte`.
