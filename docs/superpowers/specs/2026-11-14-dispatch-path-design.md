# Типизированный путь dispatch — #44

## Цель и выбранный подход

Владелец выбрал изменение формы вызова dispatch с сохранением внутреннего
объекта действия. Вместо `dispatch({ scope: 'users', type: 'SetEmailAction', email })`
потребитель вызывает `dispatch('users/SetEmailAction', { email })`.

Рассмотренная альтернатива — включить namespace во внутренний type и удалить
scope — затрагивает контракт reducer и маршрутизацию без необходимости для
запрошенного синтаксиса. Она не выбрана. Дублировать реестр действий не требуется.

## Контракт

- Допустимые пути выводятся из существующих типов действий и namespace.
  Payload соответствует выбранному действию без служебных scope/type.
- Обязательный payload нельзя пропустить. Действие без данных вызывается без
  второго аргумента. Для payload только с необязательными полями аргумент необязателен.
- Неверная пара пути и payload отклоняется, включая union-пути с несовместимыми
  payload. TypeScript сохраняет автодополнение литеральных путей.
- Для root используется явный путь `root/ActionType`.
- Внутри reducer получает прежний объект `{ ...payload, scope, type }`.
  Служебные поля задаются маршрутизацией, а не данными payload.
- Namespace и имя действия не содержат `/`: разделитель должен быть однозначным.
  Для JS/нетипизированных вызовов некорректный путь сообщается через общий канал
  ошибок dispatch без вызова reducer. Runtime-валидация бизнес-payload не вводится.
- Публичная объектная перегрузка dispatch не сохраняется. Это breaking change.
- API callbacks и эффекты продолжают возвращать объекты действий. Их выполнение
  использует общий внутренний исполнитель объектов; не требуется преобразовывать
  объект в строку и затем обратно. Новый самостоятельный runtime не создаётся.
- Сохранение state перед effects, ожидание effects/вложенных dispatch, обработка
  ошибок и успешное завершение Promise сохраняют текущую семантику.

## Область изменения

Dispatch и его типы находятся в common/fc; Svelte shell предоставляет этот API.
Обновляются внутренние адаптеры, примеры, тесты и документация. ESLint-правила,
анализирующие dispatch, проверяются на новой форме вызова и при необходимости
адаптируются. Изменение не вводит зависимость common от Svelte.

Имена существующих действий не переименовываются. Новые возможности состояния,
логирование, persistence и миграция asc-admin не входят в задачу.

Решения про обязательный `root/`, отсутствие старой перегрузки, optional payload
и обработку некорректного пути — предложения исполнителя для согласования.

## Проверка

Проверить типами правильные/неправильные namespace и имена, обязательные,
необязательные и отсутствующие payload, связь union-пути с данными и
зарезервированные поля. Runtime-тесты проверяют объект на входе reducer,
root/feature routing, некорректный путь без commit и прежние error/await contracts.
Существующие API-effect callbacks, вложенные dispatch, линтер и Svelte-пример
проходят регрессионные проверки. Перед PR: общий check, build и browser scenarios
примера, changeset для затронутых публичных пакетов.
