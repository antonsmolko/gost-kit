# createStore: Svelte-привязка

Статус: контракт согласован, интеграционное покрытие восстановлено. Основной
контракт выполнения описан в
[спеке createDispatch](../../common/docs/createDispatch.spec.md).

## Ответственность

`createStore` из `@gost-kit/svelte` создаёт реактивное состояние через
`$state.raw`, соединяет его с `createDispatch` посредством readState/writeState
и возвращает getter state вместе с dispatch и reset.

Конфигурация считывается при создании, включая ссылку на initState factory.
Фабрика вызывается как initState() без аргументов один раз при создании и ещё
один раз на каждый reset. Её результат не клонируется; обычный объект не
превращается в глубокий proxy. Отдельные store вызывают factory независимо.
Свежие вложенные значения создают scope factories; возврат общей ссылки из
factory сохраняет эту общую ссылку. Store не замораживает данные и не защищает
их от внешних мутаций.
Хранение экземпляров классов не входит в поддерживаемые сценарии; отдельного
ограничения на уровне типов или runtime-проверки для них нет.

Алгоритм dispatch, порядок commit и эффектов, вложенные вызовы, ожидание Promise
и маршрутизация ошибок проверяются в common. В createStore эти сценарии
повторно не покрываются. Контракт не включает динамическую замену обработчиков
через config и привязку this к исходному config.

Кейс параметризован по двум формам корня. |

Для SB-03 используется чистая функция presenter с явным аргументом:

```ts
const user = $derived(root.state.user);
const viewState = $derived(userPresenter(user));
```

`{ ...store.state }` создаёт новый корень с прежними ссылками вложенных объектов.
Для выбранной feature это тот же сценарий, что SB-03: корень изменился, feature
нет. Новый корень не означает, что все derived обязательно пересчитываются.

Derived должен иметь потребителя, поскольку он вычисляется лениво. Реактивные
потребители освобождаются после теста. Сами чистые функции presenter проверяются
отдельно от Svelte-привязки.

Покрытие находится в `src/shell/domain/createStore.test.ts`. Названия тестов
на английском, без префиксов ID. Для наблюдения используется один тестовый
Svelte-модуль `__tests__/observe.svelte.ts`; он исключён из пакета.

Тесты выполняются реальным клиентским Svelte runtime через существующий
Vitest-конфиг. Наблюдатель использует два отдельных derived из примера и
освобождает свой effect root после каждого сценария.

## Сброс

reset из common/fc получает ту же пару readState/writeState, что dispatch.
reset() и reset({ excluded: [] }) вызывают root factory и публикуют результат
одним writeState. reset({ excluded: ['auth'] }) сохраняет текущую ссылку auth,
остальные scopes получает из свежего root. Создание createReset само по себе
не вызывает factory. Повторный reset создаёт новые defaults.

Фабрика каждого scope строит собственные изменяемые вложения, root factory
композирует их через define.state(factory). Overrides заменяют поля по ссылке:
rootState({ users: usersState({ errors: [apiError()] }) }). Это shallow override,
не глубокое слияние. Object-вариант define.state разделяет вложенные значения
и не гарантирует их свежести; библиотека не выполняет deep clone.

Значение excluded, не являющееся массивом (в том числе null/строка/array-like
объект), отклоняется TypeError до вызова factory/readState/writeState.
Отсутствующий excluded и undefined по-прежнему означают полный сброс.

Непустой excluded разрешён для record root фиксированной структуры с
независимыми scopes. Типы отклоняют primitive/array/function/представленный union
root, но разрешают union внутри scope. Type widening/assertions могут стереть
сведения об union; runtime его не обнаруживает. Проверка прямо в filter
сопоставляет собственные поля current и initial. Недоступные с одной
из сторон ключи и унаследованные поля пропускаются; reset продолжается. Для таких
optional/временных scopes наличие и значение определяет initial. Сборка через
filter/reduce не мутирует результат factory или current; один writeState публикует
полный результат. Поддерживаются numeric/symbol keys.

Ошибка factory или подготовки результата выходит из reset синхронно; состояние
остаётся прежним. Reset не создаёт action, не запускает effects, не меняет
store/dispatch identity. Уже выполняющиеся effects не отменяются; их поздний
dispatch читает состояние после сброса и может снова заполнить scopes.
