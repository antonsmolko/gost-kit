# createStore: Svelte-привязка

Статус: контракт согласован, интеграционное покрытие восстановлено. Основной
контракт выполнения описан в
[спеке createDispatch](../../common/docs/createDispatch.spec.md).

## Ответственность

`createStore` из `@gost-kit/svelte` создаёт реактивное состояние через
`$state.raw`, соединяет его с `createDispatch` посредством readState/writeState
и возвращает getter state вместе с dispatch.

Конфигурация считывается при создании. Начальное значение не клонируется;
обычный объект не превращается в глубокий proxy. Каждый экземпляр имеет свой
текущий корень, но одинаковый переданный initState остаётся общей ссылкой до
первой замены. Store не замораживает данные и не защищает их от внешних мутаций.
Хранение экземпляров классов не входит в поддерживаемые сценарии; отдельного
ограничения на уровне типов или runtime-проверки для них нет.

Алгоритм dispatch, порядок commit и эффектов, вложенные вызовы, ожидание Promise
и маршрутизация ошибок проверяются в common. В createStore эти сценарии
повторно не покрываются. Контракт не включает динамическую замену обработчиков
через config и привязку this к исходному config.

## Интеграционные тесткейсы

| ID | Сценарий | Ожидаемый результат |
| --- | --- | --- |
| SB-01 | Создать store с обычным объектом initState. | Getter возвращает переданное значение по ссылке; store не создаёт глубокий proxy. |
| SB-02 | Наблюдать state через реального Svelte-потребителя; выполнить dispatch с новым state. | После обработки обновлений потребитель читает новый state. Проверяется соединение dispatch с реактивностью, а не повторяется тест его алгоритма. |
| SB-03 | Два derived: сначала выбрать feature state, затем вычислить presenter. Заменить другую ветку корня, сохранив ссылку feature. | Presenter не вызывается повторно; представление остаётся прежним. |
| SB-04 | Создать два store из одного config с общей исходной ссылкой; поочерёдно выполнить commit в каждом. | Каждый commit обновляет только свой store и его реактивного потребителя. Исходная общая ссылка не означает общее реактивное хранилище. |
| SB-05 | Заменить корень-примитив и массив через dispatch. | Getter и реактивный потребитель получают новое значение; объектные корни сохраняют ссылку commit. Кейс параметризован по двум формам корня. |

Для SB-03 используется чистая функция presenter с явным аргументом:

```ts
const user = $derived(root.state.user);
const viewState = $derived(userPresenter(user));
```

`{ ...store.state }` создаёт новый корень с прежними ссылками вложенных объектов.
Для выбранной feature это тот же сценарий, что SB-03: корень изменился, feature
нет. Новый корень не означает, что все derived обязательно пересчитываются.

Derived должен иметь потребителя, поскольку он вычисляется лениво. Реактивные
потребители освобождаются после теста. Сами чистые функции presenter проверяются
отдельно от Svelte-привязки.

Покрытие находится в `src/shell/domain/createStore.test.ts`. Названия тестов
на английском, без префиксов ID. Для наблюдения используется один тестовый
Svelte-модуль `__tests__/observe.svelte.ts`; он исключён из пакета.

Тесты выполняются реальным клиентским Svelte runtime через существующий
Vitest-конфиг. Наблюдатель использует два отдельных derived из примера и
освобождает свой effect root после каждого сценария.
